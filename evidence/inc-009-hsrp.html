Incident Summary

Incident INC-009
Category Network / HSRP
Protocol HSRP
Analysis Wireshark / tcpdump
Redundancy First-Hop Failover
Status Resolved

A first-hop redundancy failure prevented the expected HSRP virtual gateway from remaining available when the primary router failed. Investigation of the HSRP configuration showed that R1 and R2 were configured with different virtual IP addresses. R1 used 10.10.10.1 while R2 was incorrectly configured with 10.10.10.11. The R2 HSRP virtual IP was corrected to 10.10.10.1, after which failover and end-to-end gateway reachability were verified.

Root Cause

The HSRP redundancy configuration was inconsistent between R1 and R2. R1 and R2 were not configured with the same HSRP virtual IP address.

R1 Baseline Configuration

interface GigabitEthernet0/0
 description USER-LAN-to-SW1
 ip address 10.10.10.2 255.255.255.0
 standby version 2
 standby 1 ip 10.10.10.1
 standby 1 priority 110
 standby 1 preempt
 no shutdown

R2 Broken Configuration

interface GigabitEthernet0/0
 description USER-LAN-to-SW1
 ip address 10.10.10.3 255.255.255.0
 standby version 2
 standby 1 ip 10.10.10.11
 standby 1 priority 100
 standby 1 preempt
 no shutdown

R1 used 10.10.10.1 as the HSRP virtual IP, while R2 incorrectly used 10.10.10.11. Because the routers were not configured with the same HSRP virtual IP, R2 could not provide the expected backup path for clients using 10.10.10.1 as their default gateway.

The priority values were appropriate for the intended primary and secondary roles: R1 had priority 110 and R2 had priority 100. The configuration problem was the mismatched virtual IP, not the priority relationship.

Remediation

R2's HSRP virtual IP was corrected to match the HSRP virtual gateway configured on R1.

Corrected Configuration

 description USER-LAN-to-SW1

 standby 1 priority 100
 standby 1 preempt

The correction placed R2 into the same HSRP virtual gateway configuration as R1 while retaining the intended lower priority of 100.

Verification Result

The verification sequence demonstrated recovery of the first-hop gateway: R2 used the corrected HSRP virtual IP, successfully provided the expected virtual gateway while R1 was unavailable, PC1 successfully reached the VIP, Wireshark confirmed successful ICMP and ARP exchanges, and HSRP keepalives were observed after recovery.

Incident Closure

The HSRP failover failure was resolved and validated through configuration inspection, controlled failure testing, packet analysis, client connectivity testing, and log correlation.

  • R1 was configured with HSRP virtual IP 10.10.10.1.
  • R2 was initially configured with the incorrect virtual IP 10.10.10.11.
  • R1 failure was simulated by shutting down the primary router.
  • The expected 10.10.10.1 gateway became unavailable.
  • R2's HSRP virtual IP was corrected to 10.10.10.1.
  • R2 successfully provided the expected virtual gateway.
  • PC1 successfully reached the virtual IP after remediation.
  • Wireshark confirmed successful ARP and ICMP traffic.
  • Post-remediation HSRP keepalives confirmed continued protocol operation.

Investigation Methodology

The incident followed a structured first-hop redundancy troubleshooting workflow:

  1. Establish the client's default gateway.
  2. Verify connectivity to both physical routers.
  3. Inspect R1's HSRP configuration and state.
  4. Inspect R2's HSRP configuration and state.
  5. Compare the HSRP virtual IP configuration between peers.
  6. Identify the virtual IP mismatch.
  7. Simulate failure of the primary HSRP router.
  8. Verify client impact to the virtual gateway.
  9. Analyze HSRP and ARP packet captures.
  10. Correct the R2 HSRP virtual IP.
  11. Verify HSRP state while R1 remained unavailable.
  12. Verify client connectivity to the virtual IP.
  13. Confirm ARP and ICMP behavior with Wireshark.
  14. Confirm continued HSRP control traffic.
  15. Correlate the recovery with Splunk evidence.
  16. Document and close the incident.
