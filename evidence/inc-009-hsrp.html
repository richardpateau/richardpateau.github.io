Incident Summary

Incident INC-009
Category Network / HSRP
Protocol HSRP
Analysis Wireshark / tcpdump
Redundancy First-Hop Failover
Status Resolved

A first-hop redundancy failure prevented the expected HSRP virtual gateway from remaining available when the primary router failed. Investigation showed that R1 and R2 were configured with different HSRP virtual IP addresses. R1 used 10.10.10.1 while R2 was incorrectly configured with 10.10.10.11. When R1 failed, R2 transitioned to the Active HSRP state, but for the incorrect virtual IP. The client continued using 10.10.10.1 as its expected default gateway and could not reach that VIP. R2 was corrected to use 10.10.10.1, after which HSRP failover and client gateway reachability were successfully verified.

Root Cause

The HSRP redundancy configuration was inconsistent between R1 and R2. The routers were not configured with the same HSRP virtual IP address.

R1 Baseline Configuration

interface GigabitEthernet0/0
 description USER-LAN-to-SW1
 ip address 10.10.10.2 255.255.255.0
 standby version 2
 standby 1 ip 10.10.10.1
 standby 1 priority 110
 standby 1 preempt
 no shutdown

R2 Broken Configuration

interface GigabitEthernet0/0
 description USER-LAN-to-SW1
 ip address 10.10.10.3 255.255.255.0
 standby version 2
 standby 1 ip 10.10.10.11
 standby 1 priority 100
 standby 1 preempt
 no shutdown

R1 used 10.10.10.1 as the HSRP virtual IP, while R2 incorrectly used 10.10.10.11.

Because R2 was configured with the different virtual IP 10.10.10.11, it could not assume the virtual gateway 10.10.10.1 used by the client. When R1 failed, R2 transitioned to the Active state, but it became Active for the incorrect virtual IP. The client therefore continued attempting to resolve 10.10.10.1 and could not reach its expected default gateway.

The priority values were appropriate for the intended roles: R1 had priority 110 and R2 had priority 100. The configuration problem was the mismatched virtual IP rather than the priority relationship.

Remediation

R2's HSRP virtual IP was corrected to match the HSRP virtual gateway configured on R1 and used by the client.

Incorrect Configuration

standby 1 ip 10.10.10.11

Corrected Configuration

interface GigabitEthernet0/0
 description USER-LAN-to-SW1
 ip address 10.10.10.3 255.255.255.0
 standby version 2
 standby 1 ip 10.10.10.1
 standby 1 priority 100
 standby 1 preempt
 no shutdown

The correction placed R2 into the same HSRP virtual gateway configuration as R1 while retaining the intended lower priority of 100.

Verification Result

The verification sequence demonstrated recovery of the first-hop gateway. R2 became Active while R1 remained unavailable, R2 used the corrected virtual IP 10.10.10.1, and PC1 successfully reached the virtual gateway. Wireshark confirmed successful ARP and ICMP exchanges, while the post-remediation capture showed continued HSRPv2 hello advertisements from both routers during normal operation.

Incident Closure

The HSRP failover failure was resolved and validated through configuration inspection, controlled failure testing, packet analysis, client connectivity testing, and log correlation.

  • R1 was configured with HSRP virtual IP 10.10.10.1.
  • R2 was initially configured with the incorrect virtual IP 10.10.10.11.
  • R1 failure was simulated by shutting down the primary router.
  • R2 transitioned to the Active HSRP state, but its incorrect VIP prevented it from providing the client's expected gateway.
  • The client repeatedly attempted to resolve 10.10.10.1 during the failed state.
  • R2's HSRP virtual IP was corrected to 10.10.10.1.
  • R2 successfully provided the expected virtual gateway while R1 remained unavailable.
  • PC1 successfully reached the virtual IP after remediation.
  • Wireshark confirmed successful ARP and ICMP traffic.
  • Post-remediation HSRPv2 hello traffic confirmed continued redundancy protocol operation.

Investigation Methodology

The incident followed a structured first-hop redundancy troubleshooting workflow:

  1. Establish the client's default gateway.
  2. Verify connectivity to both physical routers.
  3. Inspect R1's HSRP configuration and state.
  4. Inspect R2's HSRP configuration and state.
  5. Compare the HSRP virtual IP configuration between peers.
  6. Identify the virtual IP mismatch.
  7. Simulate failure of the primary HSRP router.
  8. Verify R2's HSRP state after R1 failure.
  9. Verify client impact to the expected virtual gateway.
  10. Analyze HSRP and ARP packet captures.
  11. Correct the R2 HSRP virtual IP.
  12. Verify R2 as Active with the corrected virtual IP.
  13. Verify client connectivity to the virtual IP.
  14. Confirm ARP and ICMP behavior with Wireshark.
  15. Confirm continued HSRPv2 control traffic.
  16. Correlate recovery with Splunk evidence.
  17. Document and close the incident.
