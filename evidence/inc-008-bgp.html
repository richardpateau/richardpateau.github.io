Status Resolved

A public-facing destination was unreachable because R1 was configured to advertise 10.10.100.0/24 instead of the actual 10.10.10.0/24 destination. The investigation verified the BGP session, examined route advertisement from R1 and the ISP perspective, analyzed BGP packet captures, corrected the network statement, and verified end-to-end reachability.

Initial Symptoms

The incident began with failed connectivity to the web server's destination. The investigation first established that the failure was not caused by a local interface or basic routing condition on R1.

Root Cause

The BGP peering session between R1 and the ISP was operational, but R1 was configured to advertise the wrong network.

Broken BGP Configuration

router bgp 65000
 bgp log-neighbor-changes
 neighbor 192.0.2.2 remote-as 65001
 network 10.10.100.0 mask 255.255.255.0

The affected destination was the 10.10.10.0/24 network, but R1's BGP configuration referenced 10.10.100.0/24.

Because the configured BGP network statement did not identify the affected 10.10.10.0/24 prefix, R1 did not advertise that destination to the ISP. The ISP therefore did not have the required route to reach the affected network.

Corrected BGP Configuration

router bgp 65000
 bgp log-neighbor-changes
 neighbor 192.0.2.2 remote-as 65001
 network 10.10.10.0 mask 255.255.255.0

The BGP network statement was corrected to reference the actual 10.10.10.0/24 destination network.

This conclusion is supported by the before-and-after BGP configurations, R1's advertised-route output, the ISP's BGP table and routing table, packet captures, and successful post-remediation connectivity.

View Broken Configuration View Fixed Configuration

Remediation

The incorrect BGP network statement on R1 was replaced with the actual destination network, 10.10.10.0/24.

Corrected Configuration

router bgp 65000
 bgp log-neighbor-changes
 neighbor 192.0.2.2 remote-as 65001
 network 10.10.10.0 mask 255.255.255.0

This correction caused R1 to advertise the intended 10.10.10.0/24 prefix toward the ISP.

Incident Closure

The BGP route advertisement failure was resolved and validated through multiple independent checks:

  • R1 BGP configuration corrected.
  • The 10.10.10.0/24 prefix appeared in R1's BGP table.
  • R1 advertised the affected prefix.
  • The ISP learned the affected prefix.
  • The ISP routing table contained the destination.
  • End-to-end ping succeeded.
  • Post-remediation BGP packet capture confirmed the working control-plane exchange.
  • The ServiceNow-style incident was resolved and closed.

Investigation Methodology

The incident followed a structured BGP troubleshooting workflow:

  1. Confirm the public connectivity failure.
  2. Verify R1 interface state.
  3. Verify the affected route locally.
  4. Verify BGP neighbor and session state.
  5. Inspect the BGP routing table.
  6. Investigate the specific affected prefix.
  7. Inspect the BGP configuration.
  8. Verify advertised routes from R1.
  9. Correlate R1's advertisements with the ISP BGP table.
  10. Analyze BGP packet captures.
  11. Correct the BGP network statement.
  12. Verify the prefix locally and at the ISP.
  13. Confirm end-to-end connectivity.
  14. Validate the working BGP exchange with Wireshark.
  15. Document and close the incident.
