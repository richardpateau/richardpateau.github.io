INC-003 — ACL Traffic Blocked

Extended ACL troubleshooting, packet analysis, iterative remediation, and security verification.

Incident Summary

A client experienced connectivity failures when attempting to reach a server over ICMP and HTTPS. Initial testing demonstrated that both ping and HTTPS connectivity were unsuccessful.

The investigation used Cisco ACL hit counters, Splunk, Wireshark, tcpdump, and packet captures to determine whether the traffic was being blocked by the network policy.

3. Root Cause

ROOT CAUSE ANALYSIS

Multiple ACL Entries Were Blocking Required Traffic

The original ACL contained two deny statements that affected traffic from the client network to the protected server. 

ip access-list extended PROTECT-SERVER
 deny tcp any host 10.20.20.10 eq 443 log
 deny ip 10.10.10.0 0.0.0.255 host 10.20.20.10 log
 permit ip any any

The first entry explicitly denied HTTPS traffic to the server. The second entry broadly denied all IP traffic from the 10.10.10.0/24 client network to the server.

5. Remediation Attempt #1

ITERATIVE TROUBLESHOOTING

The broad IP deny was removed so that traffic from the client subnet could reach the server while preserving the explicit HTTPS and Telnet security controls. 

ip access-list extended PROTECT-SERVER
 deny tcp any host 10.20.20.10 eq 443
 deny tcp 10.10.10.0 0.0.0.255 host 10.20.20.10 eq 23
 permit ip any any
View Fix #1 Configuration →

ICMP Verification

ICMP connectivity succeeded after the first change, confirming that the broad deny had been removed as a blocking condition.

HTTPS Still Failed

HTTPS remained unavailable after Fix #1. This demonstrated that another ACL entry was still explicitly denying TCP/443.

6. Remediation Attempt #2

ACL REFINEMENT

The remaining HTTPS deny was removed while the Telnet deny was retained. This restored the required HTTPS service without removing the intended Telnet restriction. 

ip access-list extended PROTECT-SERVER
 deny tcp 10.10.10.0 0.0.0.255 host 10.20.20.10 eq 23
 permit ip any any

7. Final Verification

VERIFICATION

HTTPS Restored

HTTPS connectivity succeeded after the explicit TCP/443 deny was removed.

Telnet Remains Blocked

The final ACL continued to deny TCP/23 from the client network, demonstrating that the required HTTPS service was restored without removing the intended Telnet restriction.
